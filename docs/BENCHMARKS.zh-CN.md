## 2. 新增三轮测试

先发送一次预热请求，然后对三个用例各重复三次，总计九条正式请求。请求直接发送到本机 `127.0.0.1:8000`，不经过云端 FRP，也不包含网页登录步骤。

| 用例 | 输入 tokens | 输出 tokens | 首个输出中位数 | 生成速度中位数 | 总耗时中位数 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 算术：17 × 19 | 25 | 4 | 0.495 s | 7.80 tokens/s | 0.880 s |
| 中文：三条摄影构图建议 | 27 | 48–53 | 0.498 s | 7.72 tokens/s | 6.890 s |
| 多轮：记住相机再询问型号 | 57 | 6 | 0.717 s | 7.93 tokens/s | 1.345 s |

三个用例均通过：算术输出 323，中文回复非空且给出建议，相机型号正确包含 A7M4。这里不是严谨的模型质量评测集，也没有与其他模型做统一条件比较。

原始数据：[rtx3090-20261005.json](../benchmarks/rtx3090-20261005.json)。包含每轮原文回复、usage、首个输出时间、总耗时和汇总中位数。

## 3. 指标怎样计算

**TTFT / 首个输出时间**：从客户端开始发送请求，到读取第一个非空 `content` 增量的时间。包括输入处理和调度等待；不是每个汉字的耗时。

**生成速度**：

```text
(completion_tokens - 1) / (stream_finish_time - first_content_time)
```

从首个输出之后计算，分母包含流结束及最终 usage 的小量开销。模型每个 token 与每个 SSE chunk 不一定一一对应，因此这里是基于 usage 的近似解码速率，不是逐 token 的 GPU 内核计时。

**总耗时**：请求开始到流读取完成。输出长度不同，总耗时也不同。4 token 算术答案很短，速率比长回复更易受结束开销影响。

中文 `token` 不等于一个汉字，不能把 7.72 tokens/s 宣传成每秒 7.72 个汉字。也没有把 `completion_tokens / 总耗时` 与上述生成速度混为一谈。

## 4. 初次测试与网页测试

最早的单轮记录保存在 [qwen38-27b-chat-verified.json](../benchmarks/qwen38-27b-chat-verified.json)：

| 用例 | 首个输出 | 总耗时 | 生成速度 |
| --- | ---: | ---: | ---: |
| 第一条算术请求 | 6.603 s | 7.050 s | 6.71 tokens/s |
| 后续中文建议 | 0.468 s | 6.981 s | 7.68 tokens/s |
| 后续多轮记忆 | 0.667 s | 1.305 s | 7.84 tokens/s |

第一条请求明显更慢，应把它保留为初次请求的实际观测，不能用后续约 0.5 秒的结果替代。它不等于从 Docker 完全停止开始的完整冷启动时间，本项目没有公布严格控制的冷启动基准。

公网网页也实际生成过 31 tokens 的摄影学习介绍，页面显示约 5.6 秒；[页面截图](../assets/chat-demo.png)保留这个结果。页面计时包含浏览器、网页后端与转发路径，不能与本机模型 API 的解码速率直接混算。

## 5. 多人访问的测试结果

公网两个独立客户端分别询问 `6 × 7` 和 `8 × 9`，都得到正确回答。队列位置示例分别为 `[1, 0]` 与 `[0, 0]`：一个等待，轮到后开始；一个立即开始。

记录：[chat-queue-public-verified.json](../benchmarks/chat-queue-public-verified.json)。公开版移除了个人服务器地址。

独立受控上游的测试覆盖：

- 按进入队列的顺序开始生成。
- 等待期间每 5 秒输出队列状态，保持流连接活跃。
- 取消等待者后，不把它送进模型。
- 停止正在生成的请求后，下一条自动继续。

记录：[chat-queue-controlled-verified.json](../benchmarks/chat-queue-controlled-verified.json)。受控测试的用途是验证调度行为，其回复速度不属于 GPU 性能数据。

队列不会增加单卡生成吞吐量。总响应时间可以理解为：

```text
等待前面请求完成 + 自己的输入处理/首个输出等待 + 自己的生成时间 + 网络开销
```

最大 16 条等待消息也不是“16 路同时生成”。多人体验取决于前面的回复长度，不能根据约 7.7 tokens/s 推断高并发容量。

## 6. 自己复测

模型正常运行后，在 **Windows PowerShell 项目目录**执行：

```powershell
$python = 'C:\AIInference\runtime\chat-venv\Scripts\python.exe'
& $python scripts\benchmark_model.py --repeat 3 --output benchmark-results\model.json
```

尽量在没有其他访问者和 GPU 任务时测试，记录显卡、驱动、框架、插件提交、量化文件 SHA256、上下文限制和深入思考开关。脚本不会替你暂停正在使用的网站。

对比不同配置时，保持提示、温度、输出长度、并发和计时方式一致。长上下文、启用深入思考、显卡功耗设置、后台任务、不同量化、不同框架版本均可能改变结果。

生图部分当前没有生成耗时或成功图片记录，所以不提供“单张图多少秒”的结论。权重下载完成不是生图性能验证。

## 7. 镜像构建验证与性能数据的区别

开源版 Dockerfile 已从固定提交重新构建，并用 Qwen3-0.6B Q4_K_M 在独立容器完成真实 CUDA 生成，确认插件二进制和当前 Torch/vLLM 能一起运行。由于 27B 正在同一张显卡上服务，独立小模型测试给 KV cache 指定 64 MiB，以避开其他进程变化引起的自动显存测量错误。测试完成后已移除临时容器。

记录：[image-build-smoke-verified.json](../benchmarks/image-build-smoke-verified.json)。它是构建兼容性检查，不是 27B 测速，也没有用它的速度替代本文的 27B 原始数据。当前站点没有因为开源整理而替换正在运行的模型容器。
